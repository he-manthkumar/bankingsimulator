Transfer State Machine

Every transfer moves through at most six states. The path depends on timing, TPIN validation, and whether the credit step succeeds.

The Four Distributed Patterns

Each pattern solves a specific failure mode that would otherwise cause data loss, stuck transfers, or silent corruption.

Pattern 01 · Transactional Outbox

Guarantee the workflow always starts

The naive approach writes the transfer to MongoDB, then starts the Temporal workflow. If Temporal is unreachable between those two operations, the transfer record exists but no workflow ever runs — stuck forever.

The fix: write both the transfer document and the outbox document inside a single MongoDB multi-document transaction. Either both commit or both roll back. No half-state is possible.

handlers/transfer.go — atomic write
// single MongoDB session transaction
session.WithTransaction(ctx, func(sessCtx mongo.SessionContext) (interface{}, error) {
    db.Repo.CreateWithSession(sessCtx, session, &transfer)   // transfers collection
    db.OutboxRepo.CreateWithSession(sessCtx, session, &outbox) // outbox collection
    // if either fails → both roll back
    return nil, nil
})

The outbox entry carries status: UNPROCESSED. A background watcher goroutine monitors the collection via a MongoDB change stream and triggers the workflow when it fires.

Pattern 02 · Temporal Signal — Outbox-Ready

Decouple the HTTP handler from workflow start

If the handler calls Temporal directly (synchronously), any Temporal hiccup makes the transfer request fail for the user. Signals decouple them — the handler returns 202 immediately and the watcher bridges the gap.

outbox/watcher.go — change stream → signal
stream, _ := col.Watch(ctx, pipeline, opts) // fires on every UNPROCESSED insert
for stream.Next(ctx) {
    entry := decode(stream)
    // wake up the waiting workflow
    tc.SignalWorkflow(ctx,
        "settlement-" + entry.TransferID,
        "",
        "outbox-ready",
        nil,
    )
}
Handler → MongoDB (atomic write) → change stream → watcher → Temporal Signal → workflow resumes. The HTTP response and the workflow start are fully decoupled.
Pattern 03 · Temporal Query & Update

Live inspection and validated in-flight cancellation

Query: while the workflow is running, a getStatus query handler returns live state — countdown timer, whether debit committed, outbox ready flag. No polling the database; the workflow reports its own internal state.

Update: unlike a Signal (fire-and-forget), a Temporal Update has a validator. If the transfer is already past WAITING, the validator rejects the cancellation request and the HTTP caller gets a 409 with a reason — not a silent failure.

settlement_workflow.go — query + update handlers
// Query: live state, visible from GET /transfer/:id/status
workflow.SetQueryHandler(ctx, "getStatus", func() (WorkflowState, error) {
    return WorkflowState{
        State:            state.State,          // "WAITING" / "DEBITING" / ...
        RemainingSeconds: remaining,            // countdown for NEFT/RTGS
        DebitCompleted:   state.DebitCompleted, // did debit commit?
    }, nil
})

// Update: synchronous cancel with validation
workflow.SetUpdateHandlerWithOptions(ctx, "requestCancellation",
    func(ctx workflow.Context) error {
        state.CancelRequested = true
        cancelCh.Send(ctx, struct{}{})
        return nil
    },
    workflow.UpdateHandlerOptions{
        Validator: func(ctx workflow.Context) error {
            if state.State != "WAITING" {
                return temporal.NewApplicationError(
                    "cannot cancel: transfer is already " + state.State, "REJECTED",
                )
            }
            return nil
        },
    },
)
Pattern 04 · Saga Compensation

Undo committed operations when a later step fails

Debit commits to Postgres (money leaves sender). Then the credit call fails — Spring Boot is down, receiver account frozen, network partition. Without Saga, the money is gone. Saga registers an undo function before each step executes. On failure, it runs them all in reverse.

settlement_workflow.go — saga pattern
s := &saga.Saga{}

// register compensation BEFORE the step executes
s.AddCompensation(func(sagaCtx workflow.Context) error {
    return workflow.ExecuteActivity(sagaCtx, act.CreditAccount, CreditInput{
        AccountID:   input.FromAccount,              // ← refund the sender
        Amount:      input.Amount,
        TransferRef: input.TransferID + "-refund",
    }).Get(sagaCtx, nil)
})

// step 1: debit commits to Postgres
if err := workflow.ExecuteActivity(actCtx, act.DebitAccount, ...). ...; err != nil {
    markFailed(); return nil   // debit failed → no saga needed
}

// step 2: credit — if this fails, saga must undo step 1
if err := workflow.ExecuteActivity(actCtx, act.CreditAccount, ...)...; err != nil {
    s.Compensate(ctx)          // ← runs the refund in reverse order
    markCompensated(); return nil
}
temporal/saga/saga.go — 32-line coordinator
type Saga struct {
    compensations []func(workflow.Context) error
}

func (s *Saga) AddCompensation(fn func(workflow.Context) error) {
    s.compensations = append(s.compensations, fn)
}

func (s *Saga) Compensate(ctx workflow.Context) {
    // LIFO — last committed step is undone first
    for i := len(s.compensations) - 1; i >= 0; i-- {
        if err := s.compensations[i](ctx); err != nil {
            workflow.GetLogger(ctx).Error("compensation failed", "step", i, "error", err)
            // continue — all compensations must run regardless
        }
    }
}

The key design rule: Compensate never stops early. Even if one compensation step fails, the rest must run. Leaving other steps uncompensated would leave the system in a worse state than having a logged error.

Inside the Workflow

The SettlementWorkflow replaces what used to be a time.Sleep goroutine. It handles IMPS (0s), RTGS (15s), and NEFT (30s) with the same code path, using a selector to multiplex between three competing events.

The Selector pattern

The WAITING state uses a workflow.Selector instead of a simple sleep. This is what makes cancellation possible — the selector races the timer against the cancel signal and whichever fires first wins.

settlement_workflow.go — selector
sel := workflow.NewSelector(ctx)

timerFuture  := workflow.NewTimer(ctx, delay)           // 0s / 15s / 30s
outboxCh     := workflow.GetSignalChannel(ctx, "outbox-ready")

sel.AddFuture(timerFuture, func(_ workflow.Future) {
    state.State = "DEBITING"
})
sel.AddReceive(outboxCh, func(_ workflow.ReceiveChannel, _ bool) {
    state.OutboxReady = true
    state.State = "DEBITING"
})
sel.AddReceive(cancelCh, func(_ workflow.ReceiveChannel, _ bool) {
    state.State = "CANCELLED"
})

sel.Select(ctx)  // blocks until one fires

Why MongoDB needs a replica set

MongoDB change streams — used by the outbox watcher — require the oplog, which only exists on replica sets. A standalone mongod cannot produce change events. The compose setup bootstraps a single-node replica set on first start:

mongo-init container
// one-time initialization — runs via mongo-init service
rs.initiate({ _id: "rs0", members: [{ _id: 0, host: "mongo:27017" }] })

A single-node replica set has all the oplog machinery but none of the multi-node overhead. It is the minimum viable setup for change streams in development.

Why debit and credit are separate endpoints

The old system had one POST /transactions/settle that atomically debited and credited inside a single Postgres transaction. That's safe — but it makes Saga impossible. You cannot undo half an atomic transaction.

Old — atomic settle

BEGIN → debit → credit → COMMIT

One unit. Cannot undo partially. If credit fails, whole thing rolls back — but if it committed, there's no undo.

New — split endpoints

BEGIN → debit → COMMIT
BEGIN → credit → COMMIT

Two separate commits. Saga can target the first independently. Compensation is meaningful.

Design Decisions

Two databases, intentionally out of sync

MongoDB and PostgreSQL are intentionally desynchronized during the NEFT/RTGS settlement window. This mirrors how real banking infrastructure works — the transfer is recorded immediately, but it's not settled until the workflow completes.

ConcernTransfers (MongoDB)Balances (PostgreSQL)
Write timing T+0, before settlement begins Only after both debit and credit succeed
Schema Flexible — status evolves in-place Fixed — migration required for changes
Failure cost Duplicate or missed record Money created or destroyed
Consistency Eventual — reflects workflow progress Strong — ACID, per-endpoint transactions
"PostgreSQL is where money lives. MongoDB is where transfers happen."

Tradeoffs and honest limitations

What works well
  • Outbox pattern is fully atomic — no transfer can slip through without a workflow.
  • Saga compensation is automatic — no ops intervention needed for credit failures.
  • IMPS, NEFT, and RTGS share identical workflow code — only the delay differs.
  • Query handler eliminates polling — status reflects live workflow internal state.
Honest limitations
  • Temporal runs in dev mode (temporal server start-dev) — not production-grade persistence.
  • Fraud detection is threshold-based, not ML.
  • MongoDB replica set is single-node — no actual replication.
  • TPIN is stored as plain text — not for real production use.
