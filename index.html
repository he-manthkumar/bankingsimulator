How the Services Connect

Two critical design choices shape this flow: Gin touches MongoDB at T+0, and NEFT/RTGS transfers route through a durable Temporal workflow before PostgreSQL ever hears about them.

Streamlit (:8501) ↓ Gin (:8081) — FastAPI (:8082) — Spring Boot (:8080) ↓ ↓ MongoDB (:27017) PostgreSQL (:5432) ↘ ↙ Airflow ETL (Joins every 5 min)

Why MongoDB for Transfers?

Account balances and transfer records have completely different access patterns. Using the same database for both would be a mistake.

Concern Transfers (MongoDB) Balances (PostgreSQL)
Write timing T+0, before settlement begins Only after settlement succeeds
Schema Flexible, status evolves in-place Fixed, migration required
Operation Write + status update Atomic debit + credit (ACID)
Failure Cost Duplicate or missed record Money created or destroyed
"PostgreSQL is where money lives. MongoDB is where transfers happen."

The Two-Database Gap

MongoDB and PostgreSQL are intentionally out of sync during NEFT/RTGS settlement. This gap mirrors how real banking systems work.

  • T+0: MongoDB: PENDING | PostgreSQL: nothing
  • T+5m: Airflow runs. Pipeline UI shows IN-FLIGHT
  • T+10m: Temporal settles. MongoDB: SUCCESS | PostgreSQL: row written
  • T+15m: Next Airflow run. Both databases agree. Status SETTLED

The Problem with Goroutines

NEFT settles after 10 minutes, RTGS after 5. The naive approach in Go is to fire a goroutine that sleeps and then calls settlement.

naive_approach.go
// the naive approach
go func() {
  time.Sleep(10 * time.Minute)
  settle(transfer)  // what could go wrong?
}()

If the Gin process restarts, the goroutine dies and the transfer never settles. If Spring Boot is temporarily down, it fails silently without retries. You have zero visibility.

What Temporal Gives Us

Workflow

The full settlement process (sleep + activity). Persisted to disk, survives crashes.

Activity

The HTTP call to Spring Boot's /transactions/settle. Retried automatically.

Temporal Implementation

settlement_workflow.go
func SettlementWorkflow(ctx workflow.Context, input SettlementWorkflowInput) error {
  // durable sleep — survives process restarts
  workflow.Sleep(ctx, 10 * time.Minute)

  // Auto-retries on failure with exponential backoff
  ao := workflow.ActivityOptions{
    StartToCloseTimeout: 15 * time.Minute,
    RetryPolicy: &temporal.RetryPolicy{
      MaximumAttempts:    3,
      InitialInterval:    10 * time.Second,
      BackoffCoefficient: 2.0,
    },
  }
  
  return workflow.ExecuteActivity(
    workflow.WithActivityOptions(ctx, ao),
    act.SettleTransfer, input,
  ).Get(ctx, nil)
}
settlement_activity.go
func (a *SettlementActivity) SettleTransfer(ctx context.Context, input SettlementInput) error {
  // 1. call Spring Boot /transactions/settle
  result, err := a.BankingClient.SettleTransfer(...)
  
  status := "FAILED"
  if err == nil && result != nil {
    status = result.Status
  }

  // 2. update MongoDB status (via global db.Repo)
  db.Repo.UpdateStatus(ctx, transferID, status)

  // Temporal auto-retries if err != nil
  return err
}

Design Decisions

The correlation_id

MongoDB and PostgreSQL share no natural foreign key. This was the central design problem for Airflow reconciliation. The correlation_id is generated by Gin via uuid.New() at T+0, saved in MongoDB, and passed explicitly to Spring Boot to be saved in PostgreSQL.

Airflow sync_pipeline task
-- Exact join across two disconnected DBs
SELECT
  m.transfer_id  AS mongo_transfer_id,
  m.status       AS mongo_status,
  p.status       AS pg_status,
  p.created_at   AS settled_at
FROM mongo_transfers m
LEFT JOIN pg_transactions p
  ON m.correlation_id = p.correlation_id
Why not use transfer ID directly?

The transfer ID is MongoDB's _id. PostgreSQL doesn't know it. The correlation_id is explicitly designed to cross this boundary.

Tradeoffs and Limitations

What works well
  • Goroutine fallback keeps the simulator runnable without Temporal infrastructure.
  • Correlation ID pattern generalizes to any two-DB system.
  • Airflow idempotent upserts prevent data corruption.
Honest limitations
  • Temporal runs via start-dev locally — not production-grade.
  • Fraud detection is threshold-based, no ML.
  • Airflow batches run every 5 mins — real systems might use CDC.
